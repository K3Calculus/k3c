# K3 Patterns

## A Cookbook for Modeling Within K3d

**Version 0.1**

**Prerequisite:** K3.Base.md (the base calculus), K3d_Calc.md (deterministic specialization)

---

## Abstract

Many domains that appear to require general K3's distributional transitions — continuous-time systems, differential equations, higher-order systems, real-time constraints — can be modeled cleanly within K3d (deterministic) using well-established patterns.

This document provides worked recipes for each pattern, demonstrating the modeling technique, verifying correctness, and noting trade-offs. No distributional transitions are needed — every pattern uses the K3d 7-tuple, three meta-operators, and established axioms.

> **Principle:** If it can be modeled within K3d, it should be. General K3 exists for systems with genuinely significant unmodeled causes, not for modeling convenience.

# 1. Continuous-Time & Differential Equations

## The Challenge

K3 uses logical time (event indices). Physical systems evolve continuously. How do you model a spring-mass system, orbital mechanics, or circuit simulation in K3?

## The Pattern: Discretized Time Steps

Model continuous evolution as discrete `Tick(dt)` events. Each tick advances the simulation by a time increment `dt`, with the transition function performing numerical integration.

```text
K3_SpringMass = (S, S₀, E, G, T, N, P)

S = {
    x: ℝ,             // Position (displacement from equilibrium)
    v: ℝ,             // Velocity
    t: ℝ,             // Simulated wall-clock time
    k: ℝ,             // Spring constant
    m: ℝ,             // Mass
    damping: ℝ         // Damping coefficient
}

S₀ = { x: 1.0, v: 0.0, t: 0.0, k: 10.0, m: 1.0, damping: 0.1 }

E = Tick(dt: ℝ⁺)
    | ApplyImpulse(force: ℝ, dt: ℝ⁺)

G(s, Tick(dt)) = (dt > 0 ∧ dt ≤ 0.01, "Time step must be positive and bounded")
G(s, ApplyImpulse(_, dt)) = (dt > 0, "Time step must be positive")

// Euler integration
T_euler(s, Tick(dt)) =
    let a = (-s.k * s.x - s.damping * s.v) / s.m in
    { ...s, x: s.x + s.v * dt, v: s.v + a * dt, t: s.t + dt }

// RK4 integration (more accurate)
T_rk4(s, Tick(dt)) =
    let f(x, v) = (-s.k * x - s.damping * v) / s.m in
    let k1v = f(s.x, s.v) in
    let k1x = s.v in
    let k2v = f(s.x + k1x*dt/2, s.v + k1v*dt/2) in
    let k2x = s.v + k1v*dt/2 in
    let k3v = f(s.x + k2x*dt/2, s.v + k2v*dt/2) in
    let k3x = s.v + k2v*dt/2 in
    let k4v = f(s.x + k3x*dt, s.v + k3v*dt) in
    let k4x = s.v + k3v*dt in
    {
        ...s,
        x: s.x + (dt/6) * (k1x + 2*k2x + 2*k3x + k4x),
        v: s.v + (dt/6) * (k1v + 2*k2v + 2*k3v + k4v),
        t: s.t + dt
    }

T(s, ApplyImpulse(force, dt)) =
    let a = force / s.m in
    { ...s, v: s.v + a * dt, t: s.t + dt }

N(s) = (s.m > 0, "Mass must be positive")

P = {
    energy: s → 0.5 * s.m * s.v² + 0.5 * s.k * s.x²,    // Total energy
    amplitude: s → √(s.x² + (s.v / √(s.k / s.m))²),     // Oscillation amplitude
    phase: s → atan2(s.v / √(s.k / s.m), s.x)
}
```

## Why This Works

The differential equation `m·x'' + c·x' + k·x = F(t)` is discretized into a recurrence relation. Each `Tick` event is one step of that recurrence. The transition function is deterministic, pure, and closed — standard K3.

## Trade-offs

| Integration Method | Accuracy | Cost per Tick  | Energy Drift                          |
| ------------------ | -------- | -------------- | ------------------------------------- |
| Euler              | O(dt)    | Lowest         | High                                  |
| RK4                | O(dt⁴)   | 4× evaluations | Low                                   |
| Symplectic Euler   | O(dt)    | Low            | Very low (preserves energy structure) |
| Verlet             | O(dt²)   | Low            | Very low                              |

**Recommendation:** Use symplectic integrators for energy-preserving systems (orbital mechanics, molecular dynamics). Use RK4 for general-purpose accuracy. Guard `dt` with a maximum bound to prevent instability.

## Verification

```text
Energy conservation (undamped):
    P.energy should remain approximately constant across Tick events.

    Guard: G bounds dt to prevent numerical blowup.
    Invariant: N(s) = (s.m > 0, "Mass must be positive")
    Projection test: |P.energy(s') - P.energy(s₀)| < ε for sufficiently small dt
```

# 2. Higher-Order Systems

## The Challenge

Some systems need to modify their own rules at runtime — configurable business rules, self-modifying game mechanics, runtime-loaded plugins.

## The Pattern: Rules as State

Make the rule table part of the state. Transitions read from `s.rules` rather than being hardcoded. Events can modify rules, subject to guards and invariants.

```text
K3_Configurable = (S, S₀, E, G, T, N, P)

S = {
    data: DomainState,
    rules: Map<EventType, TransitionRule>,
    rule_version: ℕ
}

TransitionRule = {
    guard: S × E → Bool × String,     // Serialized/interpreted guard
    transform: S × E → DomainState,    // Serialized/interpreted transform
    invariant: S → Bool × String       // Additional per-rule invariant
}

S₀ = {
    data: initial_domain_state,
    rules: default_rules,
    rule_version: 0
}

E = DomainEvent(payload: Any)
    | UpdateRule(event_type: EventType, new_rule: TransitionRule)
    | RollbackRule(event_type: EventType)

G(s, DomainEvent(payload)) =
    let rule = s.rules.get(payload.type) in
    if rule = None then (false, "No rule for event type " + payload.type)
    else rule.guard(s, DomainEvent(payload))

G(s, UpdateRule(et, new_rule)) = (
    validates(new_rule) ∧ authorized(s),
    "Invalid rule or unauthorized"
)

G(s, RollbackRule(et)) = (
    s.rule_version > 0 ∧ et ∈ s.rules,
    "Nothing to rollback"
)

T(s, DomainEvent(payload)) =
    let rule = s.rules.get(payload.type) in
    { ...s, data: rule.transform(s, DomainEvent(payload)) }

T(s, UpdateRule(et, new_rule)) =
    { ...s,
      rules: s.rules.set(et, new_rule),
      rule_version: s.rule_version + 1 }

T(s, RollbackRule(et)) =
    { ...s,
      rules: s.rules.set(et, previous_rule(et)),
      rule_version: s.rule_version + 1 }

N(s) = (
    ∀rule ∈ s.rules.values: validates(rule),
    "All rules must be valid"
)
```

## Why This Works

K3 doesn't prohibit state that *describes* rules — it prohibits *modifying T, G, N at runtime* outside the calculus. By putting rules in state, modifications to rules are themselves events with guards and invariants. The actual K3 functions (G, T, N) are fixed — they *dispatch* to state-stored rules.

## Verification

This is harder than base K3 because the invariant preservation proof must hold for all *possible* rule configurations, not just the initial ones:

```text
∀rules ∈ valid_rule_configurations:
    ∀s where s.rules = rules:
        N(s) ∧ G(s, e) ⇒ N(T(s, e))
```

**Practical approach:** Constrain the space of valid rules via the `validates` function in the guard. The more constrained the rule language, the easier verification becomes.

# 3. Real-Time Constraints

## The Challenge

K3 has logical time (event indices). Real systems need wall-clock deadlines, timeouts, and scheduling guarantees.

## The Pattern: Timestamps in State + External Scheduler

Encode wall-clock time in state via event payloads. The external scheduler is responsible for injecting time-related events.

```text
K3_Timeout = (S, S₀, E, G, T, N, P)

S = {
    tasks: Map<TaskId, Task>,
    current_time: Timestamp         // Updated by external clock events
}

Task = {
    status: Pending | Running | Completed | TimedOut,
    created_at: Timestamp,
    deadline: Timestamp,
    payload: Data
}

E = CreateTask(id: TaskId, payload: Data, ttl: Duration, at: Timestamp)
    | StartTask(id: TaskId, at: Timestamp)
    | CompleteTask(id: TaskId, at: Timestamp)
    | ClockTick(at: Timestamp)              // Injected by external scheduler

G(s, CreateTask(id, _, _, _)) = (id ∉ s.tasks, "Task already exists")
G(s, StartTask(id, _)) = (
    id ∈ s.tasks ∧ s.tasks[id].status = Pending,
    "Task not pending"
)
G(s, CompleteTask(id, _)) = (
    id ∈ s.tasks ∧ s.tasks[id].status = Running,
    "Task not running"
)
G(s, ClockTick(at)) = (at ≥ s.current_time, "Time cannot go backwards")

T(s, CreateTask(id, payload, ttl, at)) = { ...s,
    tasks: s.tasks.set(id, {
        status: Pending, created_at: at,
        deadline: at + ttl, payload: payload
    }),
    current_time: at
}

T(s, StartTask(id, at)) = { ...s,
    tasks: s.tasks.update(id, t → { ...t, status: Running }),
    current_time: at
}

T(s, CompleteTask(id, at)) = { ...s,
    tasks: s.tasks.update(id, t → { ...t, status: Completed }),
    current_time: at
}

T(s, ClockTick(at)) =
    let timed_out = s.tasks.filter((id, t) →
        t.status ∈ {Pending, Running} ∧ t.deadline < at
    ) in
    { ...s,
      tasks: s.tasks.map_matching(timed_out, (id, t) → { ...t, status: TimedOut }),
      current_time: at
    }

N(s) = (
    ∀(id, t) ∈ s.tasks:
        t.status = Completed ⇒ t.created_at ≤ s.current_time,
    "Completed tasks must have valid creation time"
)
```

## Key Insight

The system doesn't call `now()` (that would violate determinism). Instead:

- Every event carries a timestamp as payload (`at: Timestamp`)
- The external scheduler injects `ClockTick` events periodically
- Timeouts are checked during `ClockTick` processing
- The guard ensures time monotonicity

During replay, the same timestamps are in the event payloads, so replay is deterministic.

# 4. Seed-Based Randomness

## The Challenge

Need randomness (shuffling, sampling, procedural generation) within K3d — without using general K3's distributional transitions.

## The Pattern: PRNG Seed in State

Thread a PRNG seed through state. Each use of randomness consumes and advances the seed deterministically.

```text
K3_CardGame = (S, S₀, E, G, T, N, P)

S = {
    deck: List<Card>,
    hands: Map<PlayerId, List<Card>>,
    discard: List<Card>,
    rng: PRNGState            // Deterministic PRNG state
}

S₀ = {
    deck: full_deck(),
    hands: {},
    discard: [],
    rng: initial_seed(42)     // Fixed seed for reproducibility
}

E = Shuffle
    | Deal(player: PlayerId, count: ℕ)
    | Reseed(seed: ℕ)         // Allows external entropy injection

G(s, Shuffle) = (|s.deck| > 0, "Nothing to shuffle")
G(s, Deal(p, n)) = (|s.deck| ≥ n, "Not enough cards")
G(s, Reseed(_)) = (true, "")

T(s, Shuffle) =
    let (shuffled, rng') = fisher_yates(s.deck, s.rng) in
    { ...s, deck: shuffled, rng: rng' }

T(s, Deal(player, count)) =
    let dealt = s.deck[0..count] in
    let remaining = s.deck[count..] in
    { ...s,
      deck: remaining,
      hands: s.hands.update(player, h → h ++ dealt),
      rng: s.rng     // Deal doesn't use randomness
    }

T(s, Reseed(seed)) = { ...s, rng: initial_seed(seed) }

N(s) = (
    |s.deck| + sum(|h| for h in s.hands.values) + |s.discard| = 52,
    "Card conservation: total cards must equal 52"
)
```

## Why This Works

`fisher_yates(deck, rng)` is a pure function: same deck + same rng → same shuffled deck + same rng'. Replay with the same initial seed produces identical shuffles. The `Reseed` event allows injecting fresh entropy while maintaining the event log for replay.

## When to Use General K3 Instead

If you need to express properties like "the probability of drawing an ace is 4/52" or verify distributional invariants (e.g., VaR bounds, expected value constraints), use general K3's distributional transitions (`T : S × E → Dist(S)`) and the Parinama Principle (`N : Dist(S) → Bool × String`). If you just need reproducible randomness within a deterministic system, seed-based K3d is simpler and more practical.

# 5. CQRS & Read Models

## The Challenge

CQRS (Command Query Responsibility Segregation) separates write models from read models. How does this map to K3?

## The Pattern: Projections Are Read Models

K3 projections ARE the read side of CQRS. Events are commands. State is the write model. Projections derive read models.

```text
K3_OrderSystem = (S, S₀, E, G, T, N, P)

// Write model (state)
S = {
    orders: Map<OrderId, Order>,
    inventory: Map<ProductId, ℕ>
}

// Events = Commands
E = PlaceOrder(id: OrderId, items: List<(ProductId, ℕ)>)
    | ShipOrder(id: OrderId)
    | CancelOrder(id: OrderId)
    | RestockProduct(product: ProductId, quantity: ℕ)

// Read models (projections)
P = {
    // Dashboard view
    order_summary: s → {
        total: |s.orders|,
        pending: s.orders.count(o → o.status = Pending),
        shipped: s.orders.count(o → o.status = Shipped)
    },

    // Customer view (parameterized)
    customer_orders: customer_id → (s →
        s.orders.filter(o → o.customer = customer_id)
    ),

    // Inventory report
    low_stock: s →
        s.inventory.filter((p, qty) → qty < reorder_threshold(p)),

    // Analytics
    revenue: s →
        s.orders
            .filter(o → o.status = Shipped)
            .sum(o → o.total_price),

    // Search index (materialized view)
    product_search_index: s →
        s.inventory.map((p, qty) → {
            product: p,
            available: qty > 0,
            quantity: qty
        })
}
```

## Key Insight

In traditional CQRS, read models are denormalized copies updated asynchronously. In K3, projections are **computed on-demand** from the canonical state. This eliminates eventual consistency issues between write and read models — projections always reflect the latest state.

For performance, implementations may cache projection results (memoization), but this is an optimization, not a semantic concern.

## Materialized Projections via Composition

If a projection is expensive, model it as a separate K3 system maintained via bridge:

```text
OrderSystem <->[projection_mapper, Async] SearchIndex

projection_mapper(before, event, after) = match event with
    | RestockProduct(p, qty) → Some(UpdateIndex(p, after.inventory[p]))
    | PlaceOrder(_, items) → Some(UpdateBatch(items.map(i → (i.product, after.inventory[i.product]))))
    | _ → None
```

Now `SearchIndex` is a separate K3 system with its own state, optimized for read access.

# 6. Saga & Compensation

## The Pattern: State Machine with Reverse Flow

Model the saga as a single K3 system whose state tracks the forward progress and any compensation steps. Each external service interaction is an event pair (attempt + result).

```text
SagaPattern:
    Forward:  Pending → Step1_Running → Step1_Done → Step2_Running → ... → Completed
    Compensate: StepN_Failed → Compensating → ... → Compensated
```

**See K3.Misc.md §3.2 for a complete OrderSaga example.**

The key insight: compensation is just more events and transitions within the same K3 system. The saga's state machine defines which compensations are needed based on how far the forward flow progressed.

## Verification

```text
// Safety: saga state machine is valid
N(s) = (valid_state_machine(s.status), "Invalid saga state")

// Key property: all acquired resources are eventually released
// Forward: resources acquired in order
// Compensation: resources released in reverse order
// Verify: no resource leak (either completed with all refs, or compensated with none)
```

# 8. Rate Limiting

## The Challenge

Enforce rate limits (N requests per time window) within K3.

## The Pattern: Sliding Window in State

```text
K3_RateLimiter = (S, S₀, E, G, T, N, P)

S = {
    requests: List<Timestamp>,       // Timestamps of recent requests
    max_requests: ℕ,                 // Maximum requests per window
    window: Duration                 // Time window
}

S₀ = { requests: [], max_requests: 100, window: 60_seconds }

E = Request(at: Timestamp)
    | CleanupExpired(at: Timestamp)

G(s, Request(at)) =
    let active = s.requests.filter(t → at - t < s.window) in
    (|active| < s.max_requests, "Rate limit exceeded: " + |active| + "/" + s.max_requests)

G(s, CleanupExpired(at)) = (true, "")

T(s, Request(at)) =
    { ...s, requests: s.requests.filter(t → at - t < s.window) ++ [at] }

T(s, CleanupExpired(at)) =
    { ...s, requests: s.requests.filter(t → at - t < s.window) }

N(s) = (
    |s.requests| ≤ s.max_requests * 2,    // Bounded growth (cleanup may lag)
    "Request list too large — cleanup needed"
)

P = {
    remaining: s → s.max_requests - |s.requests.filter(t → current_time - t < s.window)|,
    utilization: s → |s.requests| / s.max_requests
}
```

## Variants

| Algorithm      | State Needed                              | Accuracy               | Memory |
| -------------- | ----------------------------------------- | ---------------------- | ------ |
| Fixed window   | `{ count: ℕ, window_start: Timestamp }`   | Low (boundary effects) | O(1)   |
| Sliding window | `{ requests: List<Timestamp> }`           | High                   | O(n)   |
| Token bucket   | `{ tokens: ℝ, last_refill: Timestamp }`   | Medium                 | O(1)   |
| Leaky bucket   | `{ queue: List<Request>, drain_rate: ℝ }` | High                   | O(n)   |

All variants are standard K3 — timestamps arrive via event payloads, state tracks the relevant counters.

# 9. Undo/Redo

## The Pattern: Command History in State

```text
K3_UndoRedo = (S, S₀, E, G, T, N, P)

S = {
    document: DocumentState,
    undo_stack: List<(E, DocumentState)>,    // (event, state_before)
    redo_stack: List<(E, DocumentState)>
}

E = Edit(action: EditAction)
    | Undo
    | Redo

G(s, Edit(_)) = (true, "")
G(s, Undo) = (|s.undo_stack| > 0, "Nothing to undo")
G(s, Redo) = (|s.redo_stack| > 0, "Nothing to redo")

T(s, Edit(action)) =
    let new_doc = apply_edit(s.document, action) in
    { document: new_doc,
      undo_stack: s.undo_stack ++ [(Edit(action), s.document)],
      redo_stack: [] }   // New edit clears redo stack

T(s, Undo) =
    let (last_event, prev_state) = s.undo_stack.last in
    { document: prev_state,
      undo_stack: s.undo_stack.init,
      redo_stack: s.redo_stack ++ [(last_event, s.document)] }

T(s, Redo) =
    let (event, prev_state) = s.redo_stack.last in
    { document: apply_edit(prev_state, event.action),
      undo_stack: s.undo_stack ++ [(event, prev_state)],
      redo_stack: s.redo_stack.init }

N(s) = (
    |s.undo_stack| ≤ max_undo_depth,
    "Undo stack too deep"
)
```

## Key Insight

Undo/redo is itself a K3 system. The "meta" operations (undo, redo) are events like any other, with guards (can't undo empty stack) and invariants (bounded stack depth). The undo stack stores snapshots of document state — replay of the original edit events would also work but is slower.

# 10. Configuration & Feature Flags

## The Pattern: Config as State, Changes as Events

```text
K3_FeatureFlags = (S, S₀, E, G, T, N, P)

S = {
    flags: Map<FlagName, FlagConfig>,
    audit_log: List<ConfigChange>
}

FlagConfig = {
    enabled: Bool,
    rollout_percentage: ℕ,    // 0-100
    allowed_tenants: Set<TenantId>,
    updated_by: UserId,
    updated_at: Timestamp
}

E = EnableFlag(flag: FlagName, by: UserId, at: Timestamp)
    | DisableFlag(flag: FlagName, by: UserId, at: Timestamp)
    | SetRollout(flag: FlagName, percentage: ℕ, by: UserId, at: Timestamp)
    | AddTenant(flag: FlagName, tenant: TenantId, by: UserId, at: Timestamp)

G(s, EnableFlag(f, _, _)) = (f ∈ s.flags, "Unknown flag: " + f)
G(s, SetRollout(_, pct, _, _)) = (pct ≥ 0 ∧ pct ≤ 100, "Percentage must be 0-100")

T(s, EnableFlag(f, by, at)) = { ...s,
    flags: s.flags.update(f, c → { ...c, enabled: true, updated_by: by, updated_at: at }),
    audit_log: s.audit_log ++ [{flag: f, action: "enabled", by: by, at: at}]
}

// ... other transitions follow the same pattern

N(s) = (
    ∀(f, c) ∈ s.flags: c.rollout_percentage ≥ 0 ∧ c.rollout_percentage ≤ 100,
    "Rollout percentage out of range"
)

P = {
    is_enabled: (flag, tenant, user_hash) → (s →
        let c = s.flags.get(flag) in
        c.enabled ∧ (tenant ∈ c.allowed_tenants ∨ user_hash % 100 < c.rollout_percentage)
    ),
    active_flags: s → s.flags.filter((_, c) → c.enabled).keys,
    recent_changes: s → s.audit_log.last(10)
}
```

## Why K3 Fits

Feature flags are a classic case of "state that changes the behavior of other state." In K3, this is natural: the flag configuration IS state, changes to flags ARE events, and the `is_enabled` projection provides the read interface. The audit log is state, not a side-effect — it's replayable.

# 11. Recursive & Tree-Structured State

## The Challenge

Modeling file systems, organizational hierarchies, ASTs, or any tree/graph structure.

## The Pattern: Flat Maps with Parent References

```text
K3_FileSystem = (S, S₀, E, G, T, N, P)

S = {
    nodes: Map<NodeId, FSNode>,
    next_id: ℕ
}

FSNode = {
    name: String,
    parent: Option<NodeId>,
    node_type: File(content: Bytes) | Directory,
    created_at: Timestamp,
    modified_at: Timestamp
}

S₀ = {
    nodes: { 0: { name: "/", parent: None, node_type: Directory, ... } },
    next_id: 1
}

E = CreateFile(parent: NodeId, name: String, content: Bytes, at: Timestamp)
    | CreateDir(parent: NodeId, name: String, at: Timestamp)
    | MoveNode(id: NodeId, new_parent: NodeId, at: Timestamp)
    | DeleteNode(id: NodeId, at: Timestamp)

G(s, CreateFile(parent, name, _, _)) = (
    parent ∈ s.nodes ∧
    s.nodes[parent].node_type = Directory ∧
    ¬name_exists(s, parent, name),
    "Parent not a directory or name conflict"
)

G(s, MoveNode(id, new_parent, _)) = (
    id ∈ s.nodes ∧ new_parent ∈ s.nodes ∧
    ¬is_ancestor(s, id, new_parent),     // Prevent circular references
    "Invalid move: would create cycle"
)

G(s, DeleteNode(id, _)) = (
    id ∈ s.nodes ∧ id ≠ 0 ∧              // Can't delete root
    children(s, id) = {},                  // Must be empty (or use recursive delete)
    "Cannot delete: not empty or is root"
)

N(s) = (
    ∀(id, node) ∈ s.nodes:
        node.parent = None ⇔ id = 0,      // Only root has no parent
    "Tree structure violated"
) ∧ (
    ¬has_cycle(s.nodes),
    "Cycle detected in file system"
)

P = {
    path: id → (s → compute_path(s.nodes, id)),
    children: id → (s → s.nodes.filter((_, n) → n.parent = Some(id))),
    tree_size: s → |s.nodes|,
    depth: id → (s → compute_depth(s.nodes, id))
}
```

## Key Insight

Trees are stored flat (Map<NodeId, Node>) with parent pointers. The tree structure is an invariant property, not a data structure feature. K3's invariant checks ensure no cycles form and the root is unique.

# 12. Batch Processing

## The Challenge

Processing large collections of items with progress tracking, error handling, and resume capability.

## The Pattern: Cursor-Based State Machine

```text
K3_BatchProcessor = (S, S₀, E, G, T, N, P)

S = {
    items: List<Item>,
    cursor: ℕ,                    // Current position
    results: Map<ℕ, Result>,
    errors: Map<ℕ, Error>,
    status: Ready | Processing | Paused | Completed | Failed,
    batch_size: ℕ
}

S₀ = { items: input_items, cursor: 0, results: {}, errors: {}, status: Ready, batch_size: 100 }

E = StartBatch
    | ProcessNext(result: Result)
    | ProcessNextError(error: Error)
    | Pause
    | Resume
    | SkipItem
    | Complete

G(s, StartBatch) = (s.status = Ready, "Must be ready")
G(s, ProcessNext(_)) = (s.status = Processing ∧ s.cursor < |s.items|, "Not processing or no items left")
G(s, Pause) = (s.status = Processing, "Not processing")
G(s, Resume) = (s.status = Paused, "Not paused")
G(s, Complete) = (s.cursor ≥ |s.items|, "Not all items processed")

T(s, StartBatch) = { ...s, status: Processing }
T(s, ProcessNext(result)) = { ...s,
    results: s.results.set(s.cursor, result),
    cursor: s.cursor + 1 }
T(s, ProcessNextError(err)) = { ...s,
    errors: s.errors.set(s.cursor, err),
    cursor: s.cursor + 1 }
T(s, Pause) = { ...s, status: Paused }
T(s, Resume) = { ...s, status: Processing }
T(s, Complete) = { ...s, status: Completed }

N(s) = (
    s.cursor ≤ |s.items| ∧
    |s.results| + |s.errors| = s.cursor,
    "Cursor and results out of sync"
)

P = {
    progress: s → s.cursor * 100 / |s.items|,
    error_rate: s → |s.errors| * 100 / max(s.cursor, 1),
    remaining: s → |s.items| - s.cursor,
    eta: (s, avg_time_per_item) → (|s.items| - s.cursor) * avg_time_per_item
}
```

## Key Insight

The batch processor is a K3 state machine where each item processing is an event. Resume after failure is trivial — replay events up to the failure point, then continue from the cursor position. The invariant ensures cursor and results stay synchronized.

# Pattern Summary

| Pattern          | Key Technique                           | K3 Primitive Used          |
| ---------------- | --------------------------------------- | -------------------------- |
| Continuous time  | Tick(dt) events + numerical integration | T (transition)             |
| Higher-order     | Rules as state, dispatch in T           | S (state), G (guard)       |
| Real-time        | Timestamps in event payloads            | E (events), G (guards)     |
| Randomness       | PRNG seed in state                      | S (state), T (transition)  |
| CQRS             | Projections = read models               | P (projection)             |
| Saga             | State machine + compensation events     | G (guards), T (transition) |
| Rate limiting    | Sliding window in state                 | S (state), G (guard)       |
| Undo/redo        | History stack in state                  | S (state), E (events)      |
| Feature flags    | Config as state, changes as events      | S, E, P (projection)       |
| Trees/graphs     | Flat maps + parent refs + invariants    | S (state), N (invariant)   |
| Batch processing | Cursor + state machine                  | S, G, N                    |

In every case, the base 7-tuple is sufficient. The patterns are **modeling techniques**, not extensions to the calculus.
