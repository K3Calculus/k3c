# K3 Compliance Levels

## KC (Kulkarni Calculus) Compliance Standard

**Version 0.1**

This document defines the formal compliance levels for K3 implementations. For the calculus itself, see **K3.Base.md**. For the deterministic specialization, see **K3d_Calc.md**. For implementation guidance, see **K3.Impl.md**.

---

## Overview

KC Compliance Levels define a formal standard for K3 runtime implementations. Each level specifies required primitives, operators, and guarantees. Levels are cumulative — each includes all requirements of previous levels.

Implementations may comply using either the **general K3** types (`T : S × E → Dist(S)`, `N : Dist(S) → Bool × String`) or the **K3d** restriction (`T : S × E → S`, `N : S → Bool × String`). K3d compliance is valid at every level and is the expected choice for the vast majority of practical systems. General K3 compliance is required only when systems model significant unmodeled causes (see K3.Base.md §1).

| Level    | Name                    | Core Capability                                       | K3 Coverage              |
| -------- | ----------------------- | ----------------------------------------------------- | ------------------------ |
| **KC-1** | Core Semantics          | State transitions with guards and invariants          | S, S₀, E, G, T, N        |
| **KC-2** | Observable Semantics    | Projections and observability                         | + P                      |
| **KC-3** | Traceable Semantics     | Simulation with replay (replay, fuzz, golden streams) | + <?> (Samsara)          |
| **KC-4** | Compositional Semantics | Multi-system modeling                                 | + <\|\|>, <->            |
| **KC-5** | Verified Semantics      | Formal correctness proofs                             | + Verification harness   |
| **KC-6** | Certified Runtime       | Regulatory-grade audit                                | + Attestation (optional) |

## K3d vs General K3 Compliance

At each KC level, an implementation declares which type signature it supports:

| Mode           | T signature       | N signature               | Replay Mode              |
| -------------- | ----------------- | ------------------------- | ------------------------ |
| **K3d**        | `S × E → S`       | `S → Bool × String`       | Deterministic (pure)     |
| **General K3** | `S × E → Dist(S)` | `Dist(S) → Bool × String` | Seeded or distributional |

A K3d-compliant implementation is automatically compliant with general K3 at the same level (via the δ embedding: `T_general(s,e) = δ(T_det(s,e))`). The reverse is not true.

## KC-1: Core Semantics

A system is **KC-1 compliant** if it implements the fundamental K3 operational semantics with guards and invariants.

**Required Primitives:** S, S₀, E, G, T, N

**Guarantees:**

- State evolution via Apply semantics
- Guard-based event admission control
- Invariant-based safety enforcement
- Pure transition functions (Axiom 1 — determinism)
- Apply returns `ok`, `impossible`, or `violated` results

**K3d mode:** T is deterministic, Apply returns `S ∪ {⊥}`. Replay is automatic.

**General K3 mode:** T returns `Dist(S)`, N validates the distribution (Parinama Principle). Apply returns `Dist(S) ∪ {⊥}`. Implementation must support at least one sampling strategy.

---

## KC-2: Observable Semantics

A system is **KC-2 compliant** if it implements KC-1 plus projections for observability.

**Additional Primitives:** P

**Projection Classification:**

| Kind       | Purpose        | Example                            |
| ---------- | -------------- | ---------------------------------- |
| Derived    | Business logic | `net_worth = assets - liabilities` |
| Observable | Display/API    | `"Balance: ₹500"`                  |
| Metric     | Operations     | `event_count`, `latency_p99`       |

**General K3 mode:** Projections may operate on `Dist(S)` (distributional projections) in addition to `S` (state projections). Example: `expected_value: Dist(S) → ℝ`.

---

## KC-3: Traceable Semantics

A system is **KC-3 compliant** if it implements KC-2 plus the Samsara (<?>) meta-operator with replay guarantees.

**Additional:** <?> (Samsara), Trace records

**Guarantees:**

- Complete execution traceability
- Replay fidelity

**K3d mode:** Replay is deterministic — same inputs always produce same outputs. No entropy recording needed.

**General K3 mode:** Must support at least one of:
- **Seeded replay:** Record ω (unmodeled causes) alongside events. Replay with recorded ω is deterministic.
- **Distributional replay:** Replay produces identical `Dist(S)` at each step (by Axiom 1). Different ω may produce different sampled states.

**Tracing Clarification:** KC-3 compliance requires that conformance tooling (simulation, testing, verification) supports trace hooks. Tracing itself remains optional at runtime — implementations may disable trace collection for performance. The requirement is on tooling *capability*, not mandatory emission in production.

---

## KC-4: Compositional Semantics

A system is **KC-4 compliant** if it implements KC-3 plus the composition (<||>) and bridge (<->) meta-operators.

**Additional:** <||>, <-> (with all BridgeModes)

**Guarantees:**

- Algebraic system composition
- Cross-system event propagation
- Configurable failure semantics (Synchronous/Async/BestEffort)
- Isolated failure domains

**General K3 mode:** Bridge mappers may inspect `Dist(S)` of source system: `mapper(s_before, e, d_after: Dist(S₁)) → Option<E₂>`.

---

## KC-5: Verified Semantics

A system is **KC-5 compliant** if it implements KC-4 plus formal verification mechanisms.

**Required Capabilities:**

- Property-based testing (fuzz)
- Golden stream testing
- Replay equivalence assertion
- Invariant preservation verification (any strategy: testing, proof, or model checking)

**Optional Capabilities:**

- Model checking integration (TLA+, Alloy, SPIN)
- Proof assistant integration (Coq, Lean, Isabelle)
- Static analysis

**Proof obligation** (same for both modes):

```text
∀s ∈ S, e ∈ E:
    N(s) ∧ G(s, e) ⇒ N(T(s, e))

K3d:        N(s) pointwise, T(s,e) returns state
General K3: N(d) distributional, T(s,e) returns Dist(S)
```

Single proof obligation per (s, e) pair — the invariant evaluates one object (state or distribution).

---

## KC-6: Certified Runtime

A system is **KC-6 compliant** if it implements KC-5 plus regulatory-grade audit capabilities.

**Note:** KC-6 is OPTIONAL and intended for regulated industries (aviation, finance, healthcare).

**Required Capabilities:**

- Signed execution traces
- Chain of custody
- Attestation bundle
- Governance policy enforcement

**General K3 mode:** Must record ω for complete audit trail. Auditor can verify: N(d) was valid, sampled state was in support(d), and ω correctly maps to the sampled state.

| ---------------------------------------- | ----------------- | -------------- |

| Internal tools                           | KC-2              | K3d            |
| Production services                      | KC-3              | K3d            |
| Microservices, distributed systems       | KC-4              | K3d            |
| Financial, healthcare, safety-critical   | KC-5              | K3d or General |
| Quantitative trading, risk systems       | KC-5              | General K3     |
| Regulated industries, legal requirements | KC-6              | K3d or General |

## Certification Authority Model

K3 compliance certification follows a model similar to POSIX or FIDO:

- **Vendor certification**: Runtime vendors (Temporal, Axon, XState, etc.) certify their platforms against KC levels and declare K3d or General K3 support
- **Enterprise audits**: Organizations verify their K3 implementations meet required compliance levels
- **Recurring verification**: Compliance is re-verified with each major runtime release
